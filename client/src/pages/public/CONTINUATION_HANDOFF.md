# Remaining application frontend

All remaining P0/P1 screens are wired in `client/src/routes/AppRoutes.jsx`. These consume the existing injected API and canonical constants; no runtime fixtures, secondary transports or frontend-owned financial authority were added.

Public routes: `/` → Landing; `/properties` → Marketplace; `/properties/:id` → PropertyDetail. Investor routes: `/investor` → InvestorDashboard; `/investor/portfolio` → Portfolio; `/investor/portfolio/:propertyId` → HoldingDetail; `/investor/invest/:id` → InvestCheckout; `/investor/wallet` → Wallet; `/investor/kyc` → Kyc; `/investor/enquiries` → InvestorEnquiries. Admin routes: `/admin` → AdminDashboard; `/admin/properties` → AdminProperties; `/admin/properties/:id/sell` → PropertySale; `/admin/users` → AdminUsers; `/admin/kyc` → AdminKyc; `/admin/withdrawals` → AdminWithdrawals; `/admin/settings` → AdminSettings.

Admin creation/draft editing uses the existing PropertyWizard in admin mode. Published disclosure editing submits only description and images. Lifecycle changes use approve/reject/changeStatus methods, and sale submits only the preview's salePrice and expectedPlatformFeePct. PREVIEW_STALE clears the old preview and confirmation. All financial/admin actions have confirmation and pending controls.

API methods match `docs/continuation-frontend-brief.md`. `portfolio.summary()` supplies grouped holdings and allocation. The checkout uses that aggregate's ACTIVE units, current wallet availability and known property cap; it deliberately does not guess a platform cap because the published DTO has no approved public settings fields. The server validates that cap. Client calculations are labelled provisional/estimates and are never sent as authoritative purchase amounts.

`investmentIntent.mjs` retains one frozen payload and UUID after network/5xx uncertainty, rejects changed units while unresolved, and only releases it after confirmed success or a definite 4xx business failure. The checkout disables editing and offers same-key recovery on uncertain outcomes. On definite purchase failure it refreshes property, wallet and portfolio data while preserving entered units. This intent is kept in the mounted checkout's memory; leaving or reloading the checkout should be avoided while its outcome remains unconfirmed.

Wallet top-up first creates a server-signed mock order, then verifies its exact proof after confirmation. Creating an order never credits the wallet. Unknown verification outcomes retain the proof and block discarding it; duplicate confirmation instructs the user to refresh the ledger. The configured Razorpay adapter is not falsely exposed as a working mock: this frontend currently explains that only signed mock checkout is implemented. Withdrawal forms request reservations and show masked dummy bank history.

KYC only uploads dummy files with purpose `kyc`. MediaDTO URLs must provide authorized private delivery usable by the browser (for example short-lived signed delivery), not public property URLs. Own UserDTO exposes status/reason only, so an investor returning later sees those persisted fields and no fabricated document list. The administrator KYC queue uses the documented extended UserDTO with private docs/selfie. Queue/media authorization remains a server responsibility.

Shared visual helpers in `components/AppUI.jsx` include property cards, ledger tables, allocation SVG with an exact values list, KPI panels and empty-page pagination. Existing Page uses a role-aware navigation menu with accessible mobile toggle and active route state. Funding charts use server-provided series, actual uploaded imagery appears on property pages, and map embeds use validated coordinates. Every page includes the academic disclaimer.

Verification performed: root ESLint and Vite production build pass. Six frontend Node checks pass, including two new idempotency intent tests. Run `node --test client/src/features/broker/money.test.mjs client/src/pages/investor/investmentIntent.test.mjs`. Real backend browser flows and final 360/768/1440 viewport evidence are owned by the parent's integration run; these are not claimed by compile checks.

No auth provider/session implementation, server module, API client, manifest, commit, push or deployment was changed during this continuation frontend task. Refresh rotation is delegated to the parent after P0/P1 integration.
